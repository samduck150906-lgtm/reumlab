작업 전 감사에서 실제로 드러난 문제는 네 가지였다.

1. **폐기 가격이 콘텐츠 자산에 남아 있었다.** 배포 HTML은 깨끗했지만 GBP(구글 비즈니스 프로필) 붙여넣기 데이터와
   미사용 레거시 컴포넌트에 웹 49만/앱 290만/앱 카드 490만이 남아 있었다. 이 자산은 사람이 복사해 검색 표면에 올린다.
2. **축마다 제목 문형이 하나였다.** 중복 title은 0건이지만(업종명이 다르니까), 검색결과에서는 같은 문장이 업종명만 바뀌어
   100줄 늘어선 모양이었다. 의도도 갈리지 않았다 — "제작비용"으로 온 사람과 "앱개발"로 온 사람에게 같은 문형이 나갔다.
3. **`/l/` 랜딩 101개의 스니펫이 비어 있었다.** title 평균 22자, description 평균 35자.
   이 축은 "앱개발 비용", "앱개발외주 가격"처럼 계약에 가장 가까운 검색어를 받는 자리다.
4. **실제 문의 유형 중 사이트에 자리가 없는 것이 있었다.** QR 웨이팅·QR 오더, 공간대여, 세탁 정기배송,
   인력/업무관리, 관세·무역, 차량 랩핑 — 전부 "업종"이 아니라 "기능 이름"으로 들어오는 수요다.

## 2·7. 검색 의도 기반 Title / Description (CTR)

`lib/search-intent.ts` 신설. 축별로 검색 의도를 선언하고, **의도에 맞는 문형을 여러 개** 두고 slug를 시드로
결정적으로(SSG 안전) 고른다. description은 상수 문장이 아니라 **그 페이지가 실제로 가진 데이터**로 조립한다.

| 축 | 검색 의도 | 문형 수 | description 출처 |
|---|---|---|---|
| `/cost/[업종]` | 얼마인가 (cost) | 4 | 단계별 가격대 + 그 업종의 비용 요인 |
| `/app/[업종]` | 만들 수 있나·무슨 기능 (capability) | 4 | 핵심 기능 + 운영 시나리오 첫 문장 |
| `/solution/[업종]` | 어떻게 구축하나 (build) | 4 | 도입부 + 모듈 + 연동 포인트 |
| `/website/[업종]` | 홈페이지 구성·노출 (presence) | 4 | 필요 페이지 목록 + 그 업종 고유 시나리오 문장 |
| `/l/[키워드]` | 의도 8종별로 분리 | 8 + 3 | 의도별 문구 + 지역/업종 주어 |
| `/h/[허브]` | 정보 탐색 (learn) | 3 | 허브 고유 본문(`HUB_CONTENT`) 도입부 |

노출 중인 검색어에 실제로 적용된 예:

- `독서실관리앱 제작비용` → `/cost/studycafe/` : "스터디카페·독서실 앱 개발 비용, 얼마부터일까 | 기능별 견적·개발기간 | 름랩"
- `어린이집 앱개발` → `/app/childcare/` : "유치원·어린이집 앱 만들 수 있나요 | 기능·비용·개발기간 정리 | 름랩"
- `요양병원 홈페이지 제작` → `/website/yoyangbyeongwon/` : 구성형/비용형/범위형/업체형 중 시드로 선택
- `앱 개발 비용` → `/l/app-dev-cost/` : "앱개발 비용 | 580만원부터, 기능별 견적 기준 공개 | 름랩"

**title과 H1은 일부러 다르게 둔다.** H1은 페이지 안에서 읽히는 제목이고 title은 검색결과에서 클릭을 정하는 문장이다.
클릭베이트는 넣지 않았다 — 제목이 약속하는 정보(가격·기간·기능·업체 여부)는 전부 본문에 있다.

### 왜 기존 축에 넣지 않았나 (자기잠식 회피)

기존 4축은 전부 "업종"이 열쇠다. `공간대여 앱`을 `/app/party-room/`에 밀어 넣으면 그 페이지의 주제가 흐려진다.
`/system/`은 "그 기능을 어떻게 만드나(구성·기술·비용 요인)"만 다루고, 업종별 기능·비용은 기존 축으로 넘긴다.
검증: `/system/*` ↔ 업종 축 본문 유사도 최대 0.35 (임계 0.72).

## 4. 내부링크

- **업종 축 → 기능 축**: `/app`·`/cost`·`/solution` 하단에 "이 업종에서 자주 함께 찾는 기능" 블록.
  관계가 실제로 있는 30개 업종만 배선(`SYSTEMS_BY_INDUSTRY`) — 전부 연결하면 링크가 아니라 소음이다.
- **전역**: `BusinessFooter`에 `/system/` 추가 → 사이트 전 페이지에서 도달.
- **인덱스 허브 상호 배선**: `/app/` ↔ `/cost/` ↔ `/solution/` ↔ `/system/`.
- **앵커 텍스트**: "자세히 보기" 식 통일 앵커를 쓰지 않는다. 전부 문맥 앵커다 —
  "대기 손님까지 받는 웨이팅 시스템", "식당 앱 개발 비용 기준", "주문 관리자 페이지 개발", "소스코드 이관 조건 확인".

`audit-indexability`·`submit-indexnow`)은 공통 헬퍼 `scripts/read-sitemap.mjs`로 index를 따라가도록 함께 고쳤다.

## 11. Cannibalization

각 축에 `IntentProfile`(PRIMARY / SECONDARY / INTENT / DIFFERENTIATION)을 내부 데이터로 선언했다.

| 축 | PRIMARY | INTENT | DIFFERENTIATION |
|---|---|---|---|
| `/app/[업종]` | {업종} 앱 개발 | capability | 무엇을 만들 수 있는가. 금액 상세는 `/cost`로 넘긴다 |
| `/cost/[업종]` | {업종} 앱 개발 비용 | cost | 금액이 어떻게 정해지는가만. 기능 목록은 `/app`으로 넘긴다 |
| `/solution/[업종]` | {업종} 솔루션 구축 | build | 업무 시스템 관점(모듈·스택·연동·도입 단계) |
| `/website/[업종]` | {업종} 홈페이지 제작 | presence | 웹 축. 페이지 구성·검색 노출·정액 비용 |
| `/system/[기능]` | {기능} 개발 | build | 업종이 아닌 기능 이름. "그 기능을 어떻게 만드나" |

`npm run seo:verify:cannibalization` — 선언과 실제 렌더 HTML을 대조한다.
같은 업종 slug를 공유하는 축끼리 본문 Jaccard 유사도를 재고, 0.72 이상이면 DIFFERENTIATE / 0.85 이상이면 CONSOLIDATE 후보로 보고한다.
**자동으로 합치거나 지우지 않는다** — 통합은 백링크·실적을 아는 사람이 정할 일이다.

검사 결과: 137개 업종 그룹 · 임계 초과 **0쌍**. 최고 유사도 0.35 (`/app/tailor/` ↔ `/cost/tailor/`).

## 13·8·9·14. 이미 구현돼 있어 손대지 않은 항목

중복 구현을 피하려 감사 후 **의도적으로 건드리지 않은** 영역이다.

- **전환 측정(13)**: `lib/analytics.ts`에 이벤트 규약(`cta_click` / `inquiry_form_start` / `generate_lead` / `form_error`),
  page_type·service 컨텍스트, PII 차단 목록이 이미 있고 `seo:verify:conversion`이 지킨다. 새 이벤트를 만들지 않고 기존 것을 재사용했다.
- **E-E-A-T(8)**: `/source-handover/`(이관 범위·방식), `/maintenance/`(인수 점검·유지보수 방식),
  사업자 정보 푸터, `seo:verify:portfolio`의 "근거 없는 수치 0 / Review·AggregateRating 0" 검사가 이미 작동한다.
  신규 `/system/` 페이지에도 개발 과정·기술 구조·이관을 명시했고, 허위 실적은 구조적으로 차단했다.
- **구조화 데이터(9)**: 화면에 없는 FAQ를 스키마에만 넣는 사고는 `seo:verify:faq`가 이미 막고 있다(화면↔스키마 대조 통과).
  가짜 Review/AggregateRating은 0건이며 새로 만들지 않았다. `/system/`은 Service + FAQPage + BreadcrumbList를 낸다.
- **Core Web Vitals(14)**: `seo:verify:media` 기준 `<img>` 3,894개 중 alt 누락 0 · 치수 누락 0,
  `<video>` poster 누락 0. 히어로 LCP 이미지는 lazy가 아니며(`components/Analytics.tsx`가 preload 힌트를 낸다),
  본문 이미지만 `loading="lazy"`다. 신규 7페이지는 이미지 없는 텍스트 페이지라 번들·LCP 영향이 없다.

**얇은 콘텐츠(3)에 대한 판단** — 가이드 24편이 1,040~1,194자로 다른 축(1,400~1,600자)보다 짧다.
다만 이 사이트의 색인 게이트 기준은 800자이고 24편 모두 통과하며, 유사도도 임계 아래다.
글자 수를 채우려 문장을 늘리는 것은 이 작업의 원칙(검색엔진만을 위한 콘텐츠 금지)에 어긋나므로 **의도적으로 두었다.**
보강이 필요하다고 판단되면 업종별 실제 상담 사례가 쌓인 뒤 개별로 다시 쓰는 것이 맞다.
